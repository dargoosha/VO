## 1. Мета роботи

Набути практичних навичок проєктування та реалізації REST API із CRUD-операціями, організації збереження даних у PostgreSQL, контейнеризації Docker, налаштування балансування запитів між репліками сервісу та експериментального оцінювання пропускної здатності й затримки.

## 2. Постановка задачі й архітектура

Для варіанта 6 реалізовано ресурс призначення препарату. Обов'язкові поля: код пацієнта, препарат, доза, одиниці вимірювання, кратність приймання за добу, дата початку, тривалість у днях. Фільтрація виконується за назвою препарату. Валідація обмежує кратність діапазоном **1–6**, тривалість — **1–180** днів.

Запити з клієнта надходять до Nginx на порт **8080**, далі переадресовуються до одного або двох інстансів FastAPI (`web:8000`). Обидва вебінстанси звертаються до спільної PostgreSQL через внутрішню мережу Compose. База даних використовує іменований том `postgres_data`.

### 2.1. Програмне середовище та запуск

Застосунок реалізовано на Python 3.12, FastAPI і PostgreSQL 16. Nginx працює як єдина точка входу та балансувальник запитів. Для запуску необхідні Docker Desktop і Docker Compose. Після клонування репозиторію створюється файл змінних середовища на основі шаблону:

```powershell
cd prescriptions-service
Copy-Item .env.example .env
```

У `.env` необхідно встановити `POSTGRES_USER`, `POSTGRES_PASSWORD` та `POSTGRES_DB`; пароль у шаблоні замінюється на власний. Файл `.env` не публікується в Git. Після налаштування:

```powershell
docker compose up -d --build --scale web=1
docker compose ps
curl.exe http://localhost:8080/healthz
```

Swagger UI доступний за адресою `http://localhost:8080/docs`. Для переходу до двох інстансів виконується `docker compose up -d --no-build --scale web=2`. Команда `docker compose down` зупиняє середовище, зберігаючи іменований том бази даних.

### 2.2. Схема таблиці prescriptions

Структура таблиці prescriptions відповідає ORM-моделі SQLAlchemy, використаній у FastAPI. Ідентифікатор `id` є первинним ключем і створюється базою даних.

| Поле | Тип PostgreSQL / ORM | Обов'язковість | Призначення |
|---|---|---|---|
| `id` | `BIGINT`, primary key | Так | Унікальний ідентифікатор; індекс PK |
| `patient_code` | `VARCHAR(50)` | Так | Знеособлений код пацієнта |
| `drug` | `VARCHAR(200)` | Так | Назва препарату; використовується у фільтрі |
| `dose` | `NUMERIC(10,3)` | Так | Точне десяткове значення дози |
| `unit` | `VARCHAR(30)` | Так | Одиниця дози, наприклад mg |
| `frequency_per_day` | `INTEGER` | Так | Кратність приймання (1–6) |
| `start_date` | `DATE` | Так | Дата початку лікування |
| `duration_days` | `INTEGER` | Так | Тривалість (1–180 днів) |

NUMERIC(10,3) обрано, щоб уникнути похибок двійкового представлення дози; `DATE` відповідає календарній даті, а `VARCHAR` обмежує довжину тексту. Фільтрація назви препарату реалізована порівнянням `lower(drug)`; за первинним ключем `id` реалізовано адресний доступ до запису.

Для прискорення пошуку призначень за назвою препарату створено функціональний індекс idx_prescriptions_drug на виразі LOWER(drug). Оскільки фільтрація у FastAPI виконується за умовою lower(drug) = ..., індекс дозволяє PostgreSQL використовувати індексований вираз для пошуку без урахування регістру символів.
Первинний ключ id також має індекс, який автоматично створюється PostgreSQL. Він використовується для пошуку окремого призначення за ідентифікатором.

### 2.3. Контракт REST API

| Метод | Маршрут | Тіло запиту | Відповідь | HTTP-коди |
|---|---|---|---|---|
| POST | `/prescriptions` | Усі сім полів без `id` | Створений запис з `id` | 201, 400 для невалідних даних |
| GET | `/prescriptions` | Немає; `limit`, `offset`, `drug` в URL | `{"items": [...], "total": N}` | 200, 400 для невалідних параметрів |
| GET | `/prescriptions/{id}` | Немає | Один запис | 200, 404 |
| PUT | `/prescriptions/{id}` | Повний набір семи полів | Оновлений запис | 200, 400, 404 |
| DELETE | `/prescriptions/{id}` | Немає | Порожня відповідь | 204, 404 |
| GET | `/healthz` | Немає | `{"status": "ok"}` | 200, 503 за недоступності БД |

Список має `limit=20` за замовчуванням, найбільше `limit=100`; `offset` починається з нуля. Фільтр `drug` не залежить від регістру, але перевіряє **точну** назву. Заміна PUT повна, не часткова.

У застосунку передбачено обробку некоректних даних із кодом HTTP 400. Початкові експерименти виявили HTTP 500 для частини невалідних запитів, що стало підставою для додаткової перевірки серіалізації помилок валідації.

### 3.4. Перевірка валідації

Pydantic обмежує `frequency_per_day` значеннями 1–6, а `duration_days` — значеннями 1–180. Некоректні значення відхиляються кодом HTTP 400. Окремий `field_validator` забороняє ASCII-керівні символи (`ord(c) < 32` та `DEL`) у полях `patient_code`, `drug`, `unit`, зокрема нульовий символ `\u0000`, який PostgreSQL не приймає у текстових полях. У спеціальному обробнику `RequestValidationError` видаляється несеріалізовне поле `ctx` перед передаванням помилок до `jsonable_encoder`.

| Перевірка | Тестове значення | Результат |
|---|---|---|
| Мінімальна кратність | `frequency_per_day = 0` | HTTP 400 |
| Мінімальна тривалість | `duration_days = 0` | HTTP 400 |
| Максимальна тривалість | `duration_days = 181` | HTTP 400 |
| Керівний символ у коді пацієнта | `PAT-\u0000-001` | HTTP 400 |

У трьох початкових знімках перевірки меж також передавалося зайве поле `id`, тому відповідь додатково містила помилку `extra_forbidden`. Це не вплинуло на виявлення помилок у тестованих числових полях. Останній тест керівного символу проведено без зайвого поля.

### 5.1. Перевірка генератора незалежно від прикладного сервісу

Маршрут `/healthz` виконує `SELECT 1`, тому не використовується для незалежного визначення максимальної інтенсивності генератора. Для контролю застосовано мінімальний асинхронний HTTP-сервер `noop_server.py`, що працює без Docker, Nginx та PostgreSQL за адресою `127.0.0.1:9000/noop` і повертає статичну відповідь. Генератор працює одним процесом Python із циклом `asyncio`.

```powershell
# В одному терміналі
python noop_server.py
# В іншому терміналі
python load_test.py --base-url http://127.0.0.1:9000 --path-template /noop --rps 500 --warmup 10 --duration 30 --output results/generator_local_500.json
```

При цільових 500 RPS генератор запланував 15 000 запитів у вимірювальному вікні, отримав **15 000 відповідей HTTP 200**, завершив **14 998 запитів у вікні**, показав **499,93 завершень/с**, p95 = **14 мс**, p99 = **15 мс**, без винятків. Це демонструє здатність одного процесу генератора підтримувати 500 RPS на мінімальному локальному сервері. Тест того самого `/noop` через Docker+Nginx показав 7,787–8,853% винятків та затримки p95 понад 10 секунд: отже, деградація виникає в складнішому тракті, хоча з цих тестів не можна однозначно визначити конкретний компонент.

### 5.3. Аналіз перевантаження

При 10 і 100 RPS сервер стабільно обробляв запити без помилок. При 500 RPS одновебінстансна конфігурація практично втратила працездатність, тоді як друга репліка зменшила частку невдалих запитів приблизно вдвічі, проте не досягла 500 успішних відповідей за секунду.

Під час одного з тестів `docker stats` показав **99,22% CPU** вебконтейнера за обмеження `cpus: 1.0`; пам'ять становила близько 183 МіБ із 512 МіБ. Це підтверджує насичення виділеного CPU в зафіксований момент. Сервіс також використовує синхронні обробники FastAPI, один процес Uvicorn і SQLAlchemy з `pool_size=5`, `max_overflow=0`. Сукупність цих обмежень може посилювати черги й обриви з'єднань, але наведені логи без додаткової діагностики не доводять, що саме пул БД або певний тайм-аут спричинив кожен `ServerDisconnectedError`.

## 6. Балансування навантаження Nginx

У конфігурації Nginx використано Docker DNS `127.0.0.11`, динамічне визначення `web:8000` і запис поля `$upstream_addr` у журнал. ## 7. Розрахунки продуктивності

### 7.1. Прискорення та метрика Карпа—Флатта

Для двох вебінстансів використовуються формули:

\[
S = \frac{X(2)}{X(1)}, \qquad e = \frac{1/S-1/2}{1-1/2}.
\]

Величина `X` означає інтенсивність **успішних HTTP-відповідей (2xx) за секунду**, а не всі завершення запитів. При 100 RPS: `X(1)=99,97`, `X(2)=99,97`, звідси `S=1`, `e=1`. У цій точці інтенсивність обмежена генератором, тому значення метрики не характеризує частку послідовної роботи.

Для навантаження 500 RPS за медіанами трьох повторних вимірювань: `X(1)=0,987 RPS`, `X(2)=189,667 RPS`:

\[
S = \frac{189{,}667}{0{,}987} \approx 192{,}17, \qquad
 e = \frac{1/192{,}17-1/2}{1-1/2} \approx -0{,}9896.
\]

Дуже велике значення `S` пояснюється майже повною відмовою однієї репліки: медіанна частка помилок становила 99,267%, а для двох — 48,733%. Від'ємне `e` не є фізичною часткою послідовних операцій; передумови звичайної моделі прискорення порушені різними режимами помилок. Друга репліка підвищила частоту успішних відповідей, але не забезпечила сталого обслуговування 500 RPS.

### 7.2. Закон Літтла

Для стаціонарної системи закон Літтла пов'язує середню кількість запитів у системі `L`, частоту завершення `λ` та середній час перебування `W`:

\[L=\lambda W.\]

Для незалежної оцінки `L` модифікований `extra_tests_little_fixed.py` збирав кількість активних клієнтських операцій з інтервалом 10 мс. Вимірювання виконано з одним вебінстансом, 10 с прогріву та 30 с вимірювання при 100 RPS. На відміну від p95, у формулу підставляється **середній** час успішного запиту.

| Метрика | Результат повторного тесту |
|---|---:|
| Успішна інтенсивність `λ` | 100,033 зап/с |
| Середній `W` успішних запитів | ≈ 5,259 мс |
| Розрахунок `λW` | 0,5261 запиту |
| Незалежні відліки активних запитів | 6612 (номінальний інтервал 10 мс) |
| Виміряне середнє `L` | 1,2287 запиту |
| Розбіжність | 133,525% |
| p95 | 20 мс |
| Частка помилок | 0% |

За повторним тестом `L` і `λW` **не збіглися**. Тому результат не подається як підтвердження закону Літтла. Одна з причин методичної розбіжності — різні межі обліку: `L` враховує всі розпочаті клієнтські операції (також ті, що очікують у HTTP-клієнті), тоді як `W` обчислено лише для успішних відповідей; крім того, часова дискретизація у навантаженому циклі подій не гарантує інтервал рівно 10 мс. Для строгішої перевірки слід рахувати й затримки всіх запитів за узгодженими межами системи та враховувати переходи через межі вікна вимірювання. Старий прогін тривалістю 5 с з прогрівом 2 с не використовується як основний.

### 7.3. Відкритий та закритий контури

У відкритому контурі генератор надсилає запити за графіком, не очікуючи завершення попередніх; у закритому контурі кожен клієнт надсилає наступний лише після отримання результату. Цей механізм створює зворотний тиск і обмежує подальше зростання черги за фіксованої кількості клієнтів, але не гарантує меншої затримки за надмірної конкурентності.

У початковому експерименті максимальна кількість незавершених операцій відкритого контуру становила 5491, однак за умовою потрібно використовувати середнє значення `L=5028,606`. Тому для повторного закритого прогону його округлено до **5029 клієнтів**. Конектор `aiohttp.TCPConnector` переналаштовано з `limit=256` на `limit=0` (без програмного ліміту; обмеження ОС залишаються). Відкритий режим також повторено з новим конектором і порівняно з ним.

| Показник | Відкритий, 500 RPS | Закритий, 5029 клієнтів |
|---|---:|---:|
| Фактичні успішні 2xx/с | 2,400 | 1,633 |
| p95, мс | 10 951 | 12 515 |
| Частка не-2xx, % | 99,813 | 99,699 |
| Середня кількість активних клієнтських операцій | 1940,5227 | 5028,9974 |
| Пік одночасних операцій | 2127 | 5029 |

У цьому експерименті закритий режим **не дав меншого p95**: 12 515 мс проти 10 951 мс. За наявності 5029 клієнтів зворотний тиск не усуває одночасне перевантаження. Крім того, тайм-аут кожного HTTP-запиту становив 10 с, але загальний клієнтський час міг перевищувати це значення через очікування планування задач і роботу циклу подій. Показник p95 враховує також невдалі операції, а не лише успішні відповіді. Значення `active` відстежує клієнтські задачі, а не виключно запити, які реально обробляє Uvicorn. Через понад 99% помилок отримані пари `L` і `λW`, де `W` обчислювалося лише для 2xx, **не можна використовувати для перевірки закону Літтла**.

### 10.3. Docker Compose

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?required}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?required}
      POSTGRES_DB: ${POSTGRES_DB:?required}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U \"$$POSTGRES_USER\" -d \"$$POSTGRES_DB\""]
      interval: 5s
      timeout: 3s
      retries: 20
    networks: [internal]
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  web:
    build: .
    image: prescriptions-web:lab1
    pull_policy: build
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?required}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?required}
      POSTGRES_DB: ${POSTGRES_DB:?required}
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    expose: ["8000"]
    cpus: 1.0
    mem_limit: 512m
    networks: [internal]
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  nginx:
    image: nginx:stable-alpine
    ports: ["8080:80"]
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on: [web]
    networks: [internal]
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
volumes:
  postgres_data:
networks:
  internal:
    driver: bridge
```

`pull_policy: build` додано до вебсервісу в процесі налагодження локального збирання Docker. Значення цього параметра не замінює вимогу забезпечити сумісність архітектури базового образу з Docker Engine.

## 11. Розглянуті архітектурні рішення

Розглядалися допустимі альтернативи, які не порушують вимоги лабораторної:

| Альтернативне рішення | Обраний підхід | Причина вибору |
|---|---|---|
| Асинхронне підключення PostgreSQL через `asyncpg` та асинхронні сесії | Синхронний SQLAlchemy у функціях `def` | Простіша реалізація невеликого CRUD-сервісу; FastAPI виконує синхронні обробники в пулі потоків, хоча такий підхід має обмеження під навантаженням |

## 13. Висновки

У лабораторній роботі реалізовано CRUD API призначень препаратів із FastAPI, PostgreSQL, Nginx і Docker Compose. Перевірено створення, читання, повну заміну, видалення та фільтрацію записів; підтверджено індекс `LOWER(drug)` та збереження даних у Docker-томі. Незалежна перевірка генератора на локальному мінімальному ендпоінті показала 499,93 RPS без помилок. За повторного тестування предметного API при 500 RPS одновебінстансна конфігурація мала лише 0,987 успішних відповідей за секунду за медіаною трьох прогонів; дві репліки — 189,667 2xx/с. У контрольному вимірюванні використання CPU вебконтейнера досягло 99,22% виділеного одного ядра. Другий інстанс зменшив частку помилок, але не забезпечив надійну обробку 500 RPS.

У тесті закону Літтла з незалежними відліками отримано `L=1,2287` і `λW=0,5261` (розбіжність 133,525%), тобто методика потребує додаткового узгодження меж вимірювання. У порівнянні відкритого і закритого контурів за перевантаження 500 RPS обидва режими мали понад 99% невдалих запитів; закритий режим із 5029 клієнтами не покращив p95. Для контейнерів підтверджено логування з обмеженням 10 МБ на файл і до трьох файлів. Медіанний час запуску з чистим томом становив 8,44 с, розмір образу — 257,19 МіБ.
