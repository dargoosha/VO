## 2. Постановка задачі й архітектура

Для варіанта 6 реалізовано ресурс призначення препарату. Обов'язкові поля: код пацієнта, препарат, доза, одиниці вимірювання, кратність приймання за добу, дата початку, тривалість у днях. Фільтрація виконується за назвою препарату. Валідація обмежує кратність діапазоном **1–6**, тривалість — **1–180** днів.

Запити з клієнта надходять до Nginx на порт **8080**, далі переадресовуються до одного або двох інстансів FastAPI (`web:8000`). Обидва вебінстанси звертаються до спільної PostgreSQL через внутрішню мережу Compose. База даних використовує іменований том `postgres_data`.

### 2.1. Програмне середовище та запуск

Застосунок реалізовано на Python 3.12, FastAPI і PostgreSQL 16. Nginx працює як єдина точка входу та балансувальник запитів. Для запуску необхідні Docker Desktop і Docker Compose. Після клонування репозиторію створюється файл змінних середовища на основі шаблону:

```powershell
cd prescriptions-service
Copy-Item .env.example .env
```

У `.env` необхідно встановити `POSTGRES_USER`, `POSTGRES_PASSWORD` та `POSTGRES_DB`; пароль у шаблоні замінюється на власний. Файл `.env` не публікується в Git. Після налаштування:

```powershell
docker compose up -d --build --scale web=1
docker compose ps
curl.exe http://localhost:8080/healthz
```

Swagger UI доступний за адресою `http://localhost:8080/docs`. Для переходу до двох інстансів виконується `docker compose up -d --no-build --scale web=2`. Команда `docker compose down` зупиняє середовище, зберігаючи іменований том бази даних.

### 2.2. Схема таблиці prescriptions

Структура таблиці prescriptions відповідає ORM-моделі SQLAlchemy, використаній у FastAPI. Ідентифікатор `id` є первинним ключем і створюється базою даних.

| Поле | Тип PostgreSQL / ORM | Обов'язковість | Призначення |
|---|---|---|---|
| `id` | `BIGINT`, primary key | Так | Унікальний ідентифікатор; індекс PK |
| `patient_code` | `VARCHAR(50)` | Так | Знеособлений код пацієнта |
| `drug` | `VARCHAR(200)` | Так | Назва препарату; використовується у фільтрі |
| `dose` | `NUMERIC(10,3)` | Так | Точне десяткове значення дози |
| `unit` | `VARCHAR(30)` | Так | Одиниця дози, наприклад mg |
| `frequency_per_day` | `INTEGER` | Так | Кратність приймання (1–6) |
| `start_date` | `DATE` | Так | Дата початку лікування |
| `duration_days` | `INTEGER` | Так | Тривалість (1–180 днів) |

NUMERIC(10,3) обрано, щоб уникнути похибок двійкового представлення дози; `DATE` відповідає календарній даті, а `VARCHAR` обмежує довжину тексту. Фільтрація назви препарату реалізована порівнянням `lower(drug)`; за первинним ключем `id` реалізовано адресний доступ до запису.

Для прискорення пошуку призначень за назвою препарату створено функціональний індекс idx_prescriptions_drug на виразі LOWER(drug). Оскільки фільтрація у FastAPI виконується за умовою lower(drug) = ..., індекс дозволяє PostgreSQL використовувати індексований вираз для пошуку без урахування регістру символів.
Первинний ключ id також має індекс, який автоматично створюється PostgreSQL. Він використовується для пошуку окремого призначення за ідентифікатором.

### 2.3. Контракт REST API

| Метод | Маршрут | Тіло запиту | Відповідь | HTTP-коди |
|---|---|---|---|---|
| POST | `/prescriptions` | Усі сім полів без `id` | Створений запис з `id` | 201, 400 для невалідних даних |
| GET | `/prescriptions` | Немає; `limit`, `offset`, `drug` в URL | `{"items": [...], "total": N}` | 200, 400 для невалідних параметрів |
| GET | `/prescriptions/{id}` | Немає | Один запис | 200, 404 |
| PUT | `/prescriptions/{id}` | Повний набір семи полів | Оновлений запис | 200, 400, 404 |
| DELETE | `/prescriptions/{id}` | Немає | Порожня відповідь | 204, 404 |
| GET | `/healthz` | Немає | `{"status": "ok"}` | 200, 503 за недоступності БД |

Список має `limit=20` за замовчуванням, найбільше `limit=100`; `offset` починається з нуля. Фільтр `drug` не залежить від регістру, але перевіряє **точну** назву. Заміна PUT повна, не часткова.

У застосунку передбачено обробку некоректних даних із кодом HTTP 400. Початкові експерименти виявили HTTP 500 для частини невалідних запитів, що стало підставою для додаткової перевірки серіалізації помилок валідації.

### 3.4. Перевірка валідації

Pydantic обмежує `frequency_per_day` значеннями 1–6, а `duration_days` — значеннями 1–180. Некоректні значення відхиляються кодом HTTP 400. Окремий `field_validator` забороняє ASCII-керівні символи (`ord(c) < 32` та `DEL`) у полях `patient_code`, `drug`, `unit`, зокрема нульовий символ `\u0000`, який PostgreSQL не приймає у текстових полях. У спеціальному обробнику `RequestValidationError` видаляється несеріалізовне поле `ctx` перед передаванням помилок до `jsonable_encoder`.

| Перевірка | Тестове значення | Результат |
|---|---|---|
| Мінімальна кратність | `frequency_per_day = 0` | HTTP 400 |
| Мінімальна тривалість | `duration_days = 0` | HTTP 400 |
| Максимальна тривалість | `duration_days = 181` | HTTP 400 |
| Керівний символ у коді пацієнта | `PAT-\u0000-001` | HTTP 400 |

У трьох початкових знімках перевірки меж також передавалося зайве поле `id`, тому відповідь додатково містила помилку `extra_forbidden`. Це не вплинуло на виявлення помилок у тестованих числових полях. Останній тест керівного символу проведено без зайвого поля.

### 5.1. Перевірка генератора незалежно від прикладного сервісу

Маршрут `/healthz` виконує `SELECT 1`, тому не використовується для незалежного визначення максимальної інтенсивності генератора. Для контролю застосовано мінімальний асинхронний HTTP-сервер `noop_server.py`, що працює без Docker, Nginx та PostgreSQL за адресою `127.0.0.1:9000/noop` і повертає статичну відповідь. Генератор працює одним процесом Python із циклом `asyncio`.

```powershell
# В одному терміналі
python noop_server.py
# В іншому терміналі
python load_test.py --base-url http://127.0.0.1:9000 --path-template /noop --rps 500 --warmup 10 --duration 30 --output results/generator_local_500.json
```

При цільових 500 RPS генератор запланував 15 000 запитів у вимірювальному вікні, отримав **15 000 відповідей HTTP 200**, завершив **14 998 запитів у вікні**, показав **499,93 завершень/с**, p95 = **14 мс**, p99 = **15 мс**, без винятків. Це демонструє здатність одного процесу генератора підтримувати 500 RPS на мінімальному локальному сервері. Тест того самого `/noop` через Docker+Nginx показав 7,787–8,853% винятків та затримки p95 понад 10 секунд: отже, деградація виникає в складнішому тракті, хоча з цих тестів не можна однозначно визначити конкретний компонент.

У файлі `generator_local_500.json` зафіксовано середню затримку `-0,164 мс` та медіану `-0,0 мс`. Від'ємний середній час не є фізично можливим значенням тривалості HTTP-запиту. Це свідчить про особливості або похибки обліку запланованого моменту надсилання та моменту завершення в поточному генераторі.

Тому результат 499,93 успішних відповідей за секунду підтверджує досягнуту інтенсивність завершень у контрольному експерименті, але не підтверджує коректність усіх часових характеристик генератора. Оцінювання затримок потребує окремої перевірки реалізації часових вимірювань.

### 5.2. Розрахунок успішної інтенсивності

У початковому генераторі `achieved_rps_within_window` враховував усі завершення — HTTP-відповіді й винятки. Було додано `successful_completions_in_window` та `achieved_success_rps`: рахується лише HTTP 2xx, завершений у межах 30-секундного вікна. Частку помилок рахують серед запитів, запланованих у вимірювальній фазі, включно з тими, що завершилися пізніше. Для порівняння пропускної здатності використовується саме **Success RPS**.

| 1 | 100 | 99,97 | 99,97 | 5,00 | 29,00 | 38,01 | 0 | 3 |
| 1 | 500 | **0,000** | 401,30 | 112,00 | 10 985,05 | 11 360,02 | 99,627 | 3 |

| 2 | 100 | 99,97 | 99,97 | 3,00 | 24,00 | 30,00 | 0 | 3 |

### 5.3. Аналіз перевантаження

При 10 і 100 RPS сервер стабільно обробляв запити без помилок. При 500 RPS одновебінстансна конфігурація практично втратила працездатність, тоді як друга репліка зменшила частку невдалих запитів приблизно вдвічі, проте не досягла 500 успішних відповідей за секунду.

Під час одного з тестів `docker stats` показав **99,22% CPU** вебконтейнера за обмеження `cpus: 1.0`; пам'ять становила близько 183 МіБ із 512 МіБ. Це підтверджує насичення виділеного CPU в зафіксований момент. Сервіс також використовує синхронні обробники FastAPI, один процес Uvicorn і SQLAlchemy з `pool_size=5`, `max_overflow=0`. Сукупність цих обмежень може посилювати черги й обриви з'єднань, але наведені логи без додаткової діагностики не доводять, що саме пул БД або певний тайм-аут спричинив кожен `ServerDisconnectedError`.

У сирих результатах прогонів при 500 RPS переважає виняток `ServerDisconnectedError`, який означає, що клієнтське з'єднання було розірване до отримання коректної HTTP-відповіді.

Насичення CPU вебконтейнера до 99,22% підтверджує, що обмеження процесорного часу могло впливати на швидкість обробки. Один процес Uvicorn та синхронний доступ до PostgreSQL через пул SQLAlchemy на 5 з'єднань створюють додаткові потенційні вузькі місця. Проте наведені дані не дозволяють встановити єдину безпосередню причину всіх розривів. Для цього потрібна кореляція часу виникнення помилок із журналами Nginx, Uvicorn та станом пулу PostgreSQL.

Таким чином, зафіксовано насичення CPU і масові мережеві помилки, але причинний зв'язок між конкретним обмеженням і кожним обривом з'єднання залишається недоведеним.

## 7. Розрахунки продуктивності

### 7.1. Прискорення та метрика Карпа—Флатта

Для двох вебінстансів використовуються формули:

\[
S = \frac{X(2)}{X(1)}, \qquad e = \frac{1/S-1/2}{1-1/2}.
\]

Величина `X` означає інтенсивність **успішних HTTP-відповідей (2xx) за секунду**, а не всі завершення запитів. При 100 RPS: `X(1)=99,97`, `X(2)=99,97`, звідси `S=1`, `e=1`. У цій точці інтенсивність обмежена генератором, тому значення метрики не характеризує частку послідовної роботи.

Для рівня 500 RPS пропускну здатність визначено за медіаною успішних завершень HTTP 2xx у 30-секундному вимірювальному вікні:

\[
X(1)=\operatorname{median}(3{,}800;0;0)=0\ \text{зап/с},
\]

\[
X(2)=\operatorname{median}(189{,}667;168{,}633;190{,}000)=189{,}667\ \text{зап/с}.
\]

За формулою \(S=X(2)/X(1)\) прискорення для цієї точки обчислити неможливо, оскільки пропускна здатність базової конфігурації за медіаною дорівнює нулю. Відповідно, метрика Карпа—Флатта також не має коректного числового значення для цього експерименту.

Такий результат означає не нескінченне прискорення, а практичну відмову одновебінстансної конфігурації при запропонованій інтенсивності. Додавання другого інстансу відновило частину успішної обробки запитів, проте система все одно не досягла заданих 500 RPS.

Спільним ресурсом двох інстансів залишилася PostgreSQL. Додатковими обмеженнями були ресурси комп'ютера, на якому одночасно працювали генератор, Docker, Nginx і база даних. Отримані результати не дозволяють надійно відокремити внесок кожного з цих ресурсів.

Для додаткового порівняння виконано контрольні прогони при навантаженні 150 RPS. Один вебінстанс забезпечив 149,93 успішних завершення за секунду, два — 149,97. В обох випадках частка помилок становила 0%.

Формально прискорення становить \(S \approx 1{,}00023\), а метрика Карпа—Флатта — \(e \approx 0{,}99955\). Однак ці значення отримано за інтенсивності, яку обидві конфігурації повністю обслуговували, тому вони не характеризують граничну ефективність масштабування.

Водночас додавання другого інстанса зменшило p95 із 35,33 до 30 мс, а p99 — із 51,33 до 43 мс. Отже, у стабільному режимі масштабування позитивно вплинуло на затримку відповіді, хоча не збільшило фактичну інтенсивність понад задані 150 RPS.

![Рисунок 39 — Навантажувальне тестування одного вебінстансу при 150 RPS](images/web1_150.png)

![Рисунок 40 — Навантажувальне тестування двох вебінстансів при 150 RPS](images/web2_150.png)

При 100 RPS отримано \(S \approx 1\), однак це навантаження не насичує систему. Тому обчислене для нього \(e \approx 1\) не слід інтерпретувати як фізичну частку послідовного коду.

### 7.2. Перевірка закону Літтла

Закон Літтла встановлює залежність між середньою кількістю запитів у системі \(L\), інтенсивністю їх завершення \(\lambda\) та середнім часом перебування запиту в системі \(W\):

\[
L = \lambda W
\]

Для перевірки закону Літтла використано ретроспективне дискретне вимірювання кількості незавершених операцій за журналом фактичних моментів початку та завершення HTTP-запитів. Значення L обчислювалося в рівномірно розташовані моменти часу, а не безпосередньо як площа під кривою активних запитів. Це дозволило перевірити вплив інтервалу та фази дискретизації, хоча оцінки L і W використовують спільні початкові часові дані.

За результатами тестування отримано:

| Показник | Результат |
|---|---:|
| Фактична інтенсивність \(\lambda\) | 99,9 зап/с |
| Середній час відповіді \(W\) | 8,0547 мс |
| Розрахункове значення \(\lambda W\) | 0,80466 |
| Виміряне середнє \(L\), інтервал 1 мс | 0,80493 |
| Відносна розбіжність | 0,03256% |
| Середнє \(L\), інтервал 10 мс, фаза 0 мс | 0,83433 |
| Середнє \(L\), інтервал 10 мс, фаза 5 мс | 0,78426 |
| Середнє \(L\), випадкові моменти відліків | 0,81533 |
| Розбіжність випадкової вибірки | 1,5258% |
| Частка помилок | 0% |

Середній час відповіді переведено в секунди:

\[
W = 8{,}0547 / 1000 = 0{,}0080547\ \text{с}
\]

Розрахунок за законом Літтла:

\[
\lambda W = 99{,}9 \cdot 0{,}0080547 \approx 0{,}80466
\]

Відхилення між виміряним і розрахунковим значеннями становить:

\[
\delta = \frac{|0{,}80493-0{,}80466|}{0{,}80466}\cdot100\% \approx 0{,}033\%
\]

Під час попередніх перевірок із дискретними відліками спостерігалися значні розбіжності. Контрольний тест показав, що оцінка \(L\) залежить від фази спостережень: за однакового інтервалу 10 мс отримано значення 0,83433 і 0,78426. Це вказує на вплив синхронізації моментів відліків із періодичним надходженням запитів.

Застосування частіших відліків з інтервалом 1 мс дало результат 0,80493, близький до теоретичного значення 0,80466. Отже, для дослідженого режиму зі стабільним потоком запитів і без помилок отримано узгоджені результати вимірювання середньої конкурентності та перевірки закону Літтла.

![Рисунок 41 — Контрольна перевірка закону Літтла при 100 RPS](images/little_law_control.png)

### 7.3. Відкритий та закритий контури

У відкритому контурі генератор надсилає запити за графіком, не очікуючи завершення попередніх; у закритому контурі кожен клієнт надсилає наступний лише після отримання результату. Цей механізм створює зворотний тиск і обмежує подальше зростання черги за фіксованої кількості клієнтів, але не гарантує меншої затримки за надмірної конкурентності.

Для налаштування закритого контуру використано результат початкового відкритого прогону на рівні 500 RPS. Середня кількість незавершених клієнтських операцій становила `L = 5028,606`, тому кількість паралельних клієнтів округлено до 5029. Значення пікової конкурентності 5491 не використовувалося, оскільки за умовою потрібне саме середнє.

У повторному закритому прогоні обмеження `aiohttp.TCPConnector(limit=256)` змінено на `limit=0`, тобто програмний ліміт кількості з'єднань знято. При цьому залишаються обмеження операційної системи, Nginx та вебсервісу.

Контрольний відкритий прогін із новими налаштуваннями конектора дав середню кількість активних клієнтських операцій 1940,5227, що істотно відрізняється від 5028,606 початкового прогону. Таким чином, кількість клієнтів закритого контуру відповідає початковому вимірюванню, але повторні відкритий і закритий прогони не були еквівалентними за фактичною конкурентністю.

| Показник | Відкритий, 500 RPS | Закритий, 5029 клієнтів |
|---|---:|---:|
| Фактичні успішні 2xx/с | 2,400 | 1,633 |
| p95, мс | 10 951 | 12 515 |
| Частка не-2xx, % | 99,813 | 99,699 |
| Середня кількість активних клієнтських операцій | 1940,5227 | 5028,9974 |
| Пік одночасних операцій | 2127 | 5029 |

У цьому експерименті закритий режим **не дав меншого p95**: 12 515 мс проти 10 951 мс. За наявності 5029 клієнтів зворотний тиск не усуває одночасне перевантаження. Крім того, тайм-аут кожного HTTP-запиту становив 10 с, але загальний клієнтський час міг перевищувати це значення через очікування планування задач і роботу циклу подій. Показник p95 враховує також невдалі операції, а не лише успішні відповіді. Значення `active` відстежує клієнтські задачі, а не виключно запити, які реально обробляє Uvicorn. Через понад 99% помилок отримані пари `L` і `λW`, де `W` обчислювалося лише для 2xx, **не можна використовувати для перевірки закону Літтла**.

Отже, результат не підтверджує очікуваного зменшення затримки в закритому контурі. Причиною є надмірна кількість конкурентних клієнтів, значна частка невдалих операцій та відмінності між умовами початкового й повторного експериментів. Також не доведено, що всі клієнтські задачі одночасно оброблялися вебсервісом: частина могла очікувати на мережевому або клієнтському рівні. Отримані значення слід розглядати як експериментальні спостереження за перевантаженою системою, а не як доказ переваги одного режиму.

### 10.3. Docker Compose

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?required}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?required}
      POSTGRES_DB: ${POSTGRES_DB:?required}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U \"$$POSTGRES_USER\" -d \"$$POSTGRES_DB\""]
      interval: 5s
      timeout: 3s
      retries: 20
    networks: [internal]
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  web:
    build: .
    image: prescriptions-web:lab1
    pull_policy: build
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?required}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?required}
      POSTGRES_DB: ${POSTGRES_DB:?required}
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    expose: ["8000"]
    cpus: 1.0
    mem_limit: 512m
    networks: [internal]
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  nginx:
    image: nginx:stable-alpine
    ports: ["8080:80"]
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on: [web]
    networks: [internal]
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
volumes:
  postgres_data:
networks:
  internal:
    driver: bridge
```

`pull_policy: build` додано до вебсервісу в процесі налагодження локального збирання Docker. Значення цього параметра не замінює вимогу забезпечити сумісність архітектури базового образу з Docker Engine.

## 11. Розглянуті архітектурні рішення

Розглядалися допустимі альтернативи, які не порушують вимоги лабораторної:

| Альтернативне рішення | Обраний підхід | Причина вибору |
|---|---|---|
| Асинхронне підключення PostgreSQL через `asyncpg` та асинхронні сесії | Синхронний SQLAlchemy у функціях `def` | Простіша реалізація невеликого CRUD-сервісу; FastAPI виконує синхронні обробники в пулі потоків, хоча такий підхід має обмеження під навантаженням |
| Окремий контейнер для міграцій | Початкова схема в `db/init.sql` | Для однієї таблиці достатньо ініціалізації на новому томі; окремі міграції потрібні при подальших змінах існуючої схеми |
| Генерація запитів кількома процесами | Один процес із `asyncio` | Менша складність синхронізації та об'єднання вимірювань; незалежний тест 500 RPS підтвердив 499,93 RPS без помилок на мінімальному локальному сервері |

Обрані альтернативи оцінювалися за простотою реалізації, відтворюваністю та достатністю для лабораторного масштабу.

## 12. Використання генеративних моделей

Під час виконання лабораторної роботи використовувалася генеративна модель ChatGPT для підготовки початкових варіантів програмного коду, пояснення помилок Docker і FastAPI, розроблення сценаріїв навантажувального тестування та оформлення звіту.

Запропоновані рішення перевірялися практично. Зокрема, тестувалися CRUD-операції, валідація вхідних даних, робота з Docker Compose, балансування Nginx і поведінка сервісу під навантаженням.

Після тестування було виявлено недоліки початкової реалізації обробника помилок валідації та методики підрахунку продуктивності. Відповідні частини коду були скориговані, а результати перевірено повторними експериментами.

Числові показники, наведені у звіті, отримано під час запуску програмних тестів, а не згенеровано моделлю.

## 13. Висновки

У лабораторній роботі реалізовано CRUD API призначень препаратів із FastAPI, PostgreSQL, Nginx і Docker Compose. Перевірено створення, читання, повну заміну, видалення та фільтрацію записів; підтверджено індекс `LOWER(drug)` та збереження даних у Docker-томі. Після виправлення обробника валідації невалідні числові значення й керівні символи відхиляються HTTP 400.

Незалежна перевірка генератора на мінімальному локальному HTTP-сервері показала 499,93 успішних завершень за секунду при заданих 500 RPS. Водночас у результатах виявлено некоректне від'ємне значення середньої затримки, тому часові характеристики генератора потребують додаткової перевірки.

За результатами трьох повторних прогонів на рівні 500 RPS медіанна інтенсивність успішних відповідей становила 0 RPS для одного вебінстансу та 189,667 RPS для двох. Це свідчить про практичну втрату працездатності одновебінстансної конфігурації за такого навантаження. Додавання другого інстансу підвищило кількість успішних завершень, але не забезпечило обробку заданої інтенсивності без значної частки помилок.

За цих умов прискорення та метрика Карпа—Флатта для рівня 500 RPS не мають коректного числового значення через нульову медіанну пропускну здатність одного інстансу. Спільним ресурсом залишається PostgreSQL; також на вимірювання могли впливати обмеження CPU та конкуренція процесів на одному комп'ютері.

Для перевірки закону Літтла проведено додатковий контрольний експеримент при 100 RPS з одним вебінстансом. Отримано середню інтенсивність 99,9 зап/с, середній час відповіді 8,0547 мс та розрахункове значення \(\lambda W = 0{,}80466\). Дискретна оцінка середньої кількості незавершених запитів з інтервалом 1 мс дало \(L = 0{,}80493\). Розбіжність становила 0,03256%, що підтверджує узгодженість результатів із законом Літтла в дослідженому режимі. Також встановлено, що точність дискретного вимірювання залежить від інтервалу та фази відліків.

У порівнянні відкритого й закритого контурів закритий режим із 5029 клієнтами не забезпечив меншого p95. При цьому кількість клієнтів визначено за попереднім відкритим прогоном, а повторне вимірювання мало іншу середню конкурентність. Отже, отримані результати не дозволяють робити однозначний висновок про перевагу одного режиму.

Для контейнерів налаштовано обмеження журналів Docker до 10 МБ на файл і трьох файлів. Медіанний час запуску з чистим томом становив 8,44 с, розмір фінального образу — 257,19 МіБ.
